# 02 — 한국어 후보·인자와 Jev 최적화

- 상태: **IN_PROGRESS — Jev 개발 예문과 bounded 선택 경로 시험, 독립 품질 전**
- 책임: J-10, J-11, F-10. 시험: P118-02, P118-06.
- 선행: [명령/인자 등록부](01_command_contracts.md).

## 처리 경로

`출처·역할 사전 검사 → 구조화 후속 제어 분기 → 본문/참조 정규화 → 필요한 후보 조회 → Jev의 닫힌 선택 → 인자 검증 또는 명확화 → 최신 상태/확인 → 공통 서비스` 순서로 설계한다.

구조화 슬래시/버튼과 문맥에 결합한 확인·취소·페이지/번호 선택은 의미 판단이 필요하지 않으므로 Jev0회다. 정확히 문서화한 `!!창근아 도움말`, `!!창근아 주시 켜기` 같은 구조화 별칭도 별도 schema로 취급할 수 있다. **자유로운 한국어 바꿔 말하기**는 Jev를 통한 등록 후보 선택이 필요하다. 단어가 들어있다는 이유만으로 실행하는 우회를 만들지 않는다. 구조화 별칭 통과를 자유 문장 지원률에 넣지 않는다.

### 정규화와 인자

- Unicode/띄어쓰기·조사·존댓말/반말·어순·한글 수사를 정규화하되 원문 구간을 보존한다. 부정·제외·조건·시제는 제거하지 않는다.
- URL, 따옴표 제목/이름, 채널 멘션, 숫자/퍼센트/위치를 먼저 typed span으로 분리한다. 인용된 `정지`, `삭제`, `그리고`는 명령 동작이나 복합 요청 구분자로 사용하지 않는다.
- `https://` 없는 YouTube 주소는 기존 검증기로 정규화한다. 영상과 목록, 여러 URL, 링크+첨부 충돌은 명시적인 선택으로 해결한다. URL 전체를 모델이 재작성하지 않는다.
- “지금 곡”, “그 목록”, “두 번째”, “내 음성방”, “맨 뒤”는 신선한 현재 상태 또는 같은 요청자/채널의 명시된 결과 snapshot으로 해석한다. 근거 없는 최근 전역 문맥, 타인의 조회, 임의 첫 결과를 쓰지 않는다.
- 복수 채널/곡 참조는 `[채널1]`, `[곡2]` 같은 개별 불투명 ID에 결합한다. 서로 다른 참조를 모두 `[참조]`로 치환해 구별을 잃지 않는다. 실제 Discord ID·권한/역할 목록은 Jev에 보내지 않는다.
- “소리 조금 줄여줘”처럼 필요한 수치가 불명확하면 값만 질문한다. 명시적인 상대값은 최신 볼륨과 결합하고0~100 밖이면 자동 보정 없이 안내한다.

### 후보 생성과 단계

1. 역할/출처로 실행 불가능한 후보를 사전에 제외한다. 이 단계의 거절에는 Jev가 필요 없다. 단, 읽기와 편집이 섞인 문장을 잘못 사전 거절하지 않도록 명령군별 회귀를 둔다.
2. 공통 등록부의 표현/인자 단서로 의도 후보를 만들고 해당 명령군의 최소 자료만 조회한다. 카탈로그/목록/큐 전체 snapshot을 모든 문장에 무조건 읽지 않는다. 정확명·별칭·제목·명시 번호의 우선순위를 고정하고 후보 잘림/검색 한계도 결과로 남긴다.
3. 한 호출의 후보 상한은 기존10개를 유지한다. 명확한 명령·대상을 후보로 만들 수 있으면1단계에서 완성한다. 후보가 없거나 너무 많으면 안전한 거절과 **상위 명령군 선택 → 해당 명령/대상 선택**의 제한 경로를 비교한다. 상위군은10개 이하의 고정 집합이며 전체 요청의3회 예산 안에서만 사용한다. 누락 후보를 확률 점수로 복구했다고 주장하지 않는다.
4. 2단계는 부족한 명령/대상·인자를, 조건부3단계는 근거 있는 남은 참조를 해결한다. 4단계가 필요하거나 후보가 잘렸으면 질문/선택으로 종료한다. 모델은 제시된 후보 ID만 선택하며, 선택 결과에 없는 필수값을 추측하지 않는다.
5. 의도와 대상이 정해졌지만 필수 인자가 빠지면 `clarification_required`로 현재 판단을 끝낸다. 사람이 답하는 동안 provider 요청이나12초 타이머를 열어 두지 않는다. [후속 입력 계약](03_dialogue_permissions_and_responses.md)에 맞는 구조화 값/선택만 추가 호출 없이 받는다.

명령군/후보 설명은 기존 API1.2의 허용된 선택 payload 안에서 표현하는 것을 우선한다. 엄격 schema의 새 필드·새 action 값을 서버와 클라이언트 합의 없이 넣지 않는다. 호환 변경이 불가능하면 별도 schema/이관 설계를 선행하고 구버전 요청을 조용히 수용하지 않는다.

## 최적화 순서

1. **누락 명령과 정답 후보 포함률**을 먼저 개선한다. 1.1.6의15개 사전 후보 실패와 제목/부정 오인 사례를 개발 회귀에 넣는다.
2. 안정된 후보로 명령군별 설명과 필요한 인자만 전송한다. 현재 live 기준 prompt v5와0.80/0.10을 출발점으로 삼고, 1.1.6 축약 prompt는 운영 채택되지 않았다는 기록을 유지한다.
3. prompt만 바꾸는 A/B를 같은 개발 자료/상태/역할로 비교한 뒤 임계값 변경은 별도 실험으로 둔다. 정답·안전0위반·명령군 성공률이 악화되면 token/지연이 줄어도 채택하지 않는다. 자동 질문 증가로 유료 호출이 줄어든 결과도 이득으로 계산하지 않는다.
4. 정적 명령 설명·조회 계획 캐시와 기존 동일 요청/단계 합류를 재사용할 수 있다. 다른 사용자 간 의미 결과 캐시, 전체 대화 전송, 불명 요청 재시도, 요청마다 새 epoch/profile 생성은 금지한다.

최종 선택 전후에 입력 token(제공 시), UTF-8 bytes(별도), provider 호출, 후보 수/정답 포함 여부, DB 조회, 의도·대상·인자 정확도, 명확화율, 거절/timeout/취소/혼잡 분모와 p50/p95를 기록한다. 외부 내부 forward/가격은 unavailable/unknown을 유지한다.

## 유지할 상한과 종료 조건

- 요청당 **최대3단계/3dispatch**, 전체12초·단계 `min(4초, 잔여시간)`,3단계 시작 잔여1초. gateway worker1·활성1·대기4·retry0를 유지한다. 명령군 분류를 이 상한 밖의 숨은 호출로 추가하지 않는다.
- 구조화 별칭/후속 취소는 `gateway.ready()` 앞에서 처리해 Jev 장애나 대기 슬롯 때문에 취소가 막히지 않게 한다. 일반 자연어는 준비 상태를 검증한다.
- 필요한 데이터의 조회·정규화·명확화 결정 실패도 전체 지연/실패 분모에 넣는다. API 대기만 따로 재어 전체 응답 시간으로 제시하지 않는다.
- 모든 명령군이 전수 회귀와 신규 독립 평가를 통과하기 전까지 전체 자연어 지원/최적화 성공을 선언하지 않는다.
