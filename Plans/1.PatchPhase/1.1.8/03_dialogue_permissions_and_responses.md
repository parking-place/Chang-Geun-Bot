- 상태: **IN_PROGRESS — 취소/비공개 버튼/출처 일부 구현, typed continuation 미구현**
- 책임: F-11, F-12. 시험: P118-03~05.
- 선행: [등록부](01_command_contracts.md), [추론 단계](02_natural_language_pipeline.md), [입력 경계 결정](../../../docs/decisions/0009-all-command-natural-language-plan.md).

## 제한된 후속 문맥

질문·결과·확인은 guild/channel/actor/root request·원래 message·명령 ID·자료 snapshot/version·주시 세대·profile/config에 결합한다. 사용자당 서버 내 활성 보충 요청은 최대1개, TTL은60초 이내다. 원문 대화 전체를 저장하거나 다른 채널/사용자의 문맥을 이어받지 않는다.

- “어느 목록?”에는 제시한 ID/번호, “새 이름?”에는 검증된 이름 값처럼 **선택된 명령의 한정된 슬롯**만 보충한다. 원래 질문에 답장하거나 명시한 요청 식별자를 사용한다. `그거`, `응`만으로 임의 작업을 찾지 않는다.
- 문맥 값 보충은 의미 판단이 끝난 요청의 구조화 단계다. 원래 inference 요청은12초 안에 영구 종료하고, 서버가 **완성 전 typed intent와 허용 슬롯에만 결합한 단회 continuation capability**를 발급한다. 이 capability의 별도 TTL은최대60초다. 새 provider 호출·원래12초 기한 연장·3회 누계 초기화는 없다.
- 답장을 받으면 capability·원래 root/trace/호출 누계·snapshot·최신 권한/출처를 검사하고 별도의 파생 실행 request ID로 완성된 새 plan을 만든다. 실행 유효기간은 `min(답장 수신+12초, capability 만료)` 이내로 둔다. 이는 사용자 구조화 답변의 로컬 실행 기한이며 provider 기한을 다시 여는 권한이 아니다. 기존 만료된 `ActionPlan.expires_at`을 고치거나 예외로 실행하지 않는다. 부모 trace를 추적하고 가짜0단계 추론 성공을 만들지 않는다. 파생 plan에도 필요한 실행 확인은 별도로 발급한다.
- 질문 대기 동안 원래 inference는 종료됐어도 message ledger는 취소 가능한 `waiting`으로 유지하고, 현재 `on_message`의 일괄 `finish` 경로가 대기를 지우지 않도록 바꾼다. 목표가 바뀐 자유 문장은 기존 pending을 종료하고 명시적으로 새 사용자 요청을 접수한다. 같은 실패 문장을 자동 재전송하지 않는다.
- 모호한 슬롯 답변은 추가 질문 또는 새 요청을 안내하고 실행하지 않는다. 동작 변경 문장을 새 이름/태그로 오해해 저장하지 않는다. 값에 동작어가 필요한 경우 인용/선택으로 명시하게 한다.
- 표시 번호는 원래 결과 snapshot의 안정적인 ID로 변환한다. 새로고침은 새 읽기 request ID를 만들며 변경 실행 ID와 재사용하지 않는다. 1.1.3의 조회/실행 ID 충돌을 회귀에 포함한다.

## 실행 확인과 취소

명확화는 대상을 정하는 절차이고, 파괴적 실행 확인은 별도다. 목록 삭제·큐 비우기·생성/가져오기·교체·대량 변경·음성 이동·되돌리기와 자연어 항목 제거의 기존 확인 규칙을 유지한다.

확인은 정확한 변경 미리보기와 결합한 버튼 또는 그 미리보기에 대한 `!!창근아 그대로 진행해` 답장만 받는다. 작성자·출처·version/revision·TTL·단회 token을 다시 검사하고 실제 동작/영향이 달라지면 새 확인을 받는다. 모델의 “확인됨” 응답, 과거 동의, 대상 선택으로 확인을 대신하지 않는다.

`!!창근아 내 요청 취소해`는 원래 요청의 소유권을 확인하는 구조화 제어로, 일반2초 cooldown·이미 진행 중인 사용자 슬롯·Jev 대기 앞에서 처리한다. 본인의 동일 출처 활성 요청만 취소하고 원자적 커밋 경쟁에서 한 결과만 남긴다. 커밋 후에는 늦음 상태를 알리며 이미 실행된 편집을 undo하거나 현재곡을 정지하지 않는다. 주시 해제로 일반 입력 경로가 닫혀도 원래 취소 버튼은 소유권 검사 후 사용할 수 있게 한다.

## 관리자 자연어와 복구 경로

새 1.1.8 계획에서 일반 prefix와 관리자 복구 출처를 구분한다.

| 출처/상태 | 허용할 입력 |
| --- | --- |
| 정상 등록·주시 켜짐 텍스트 채널 | 현재 권한에 맞는 자연어; 주시/운영도 관리자에게만 허용 |
| 주시 꺼짐 또는 미등록이지만 기존 정적 text allowlist에 있는 채널 | 서버 소유자/서버 관리 권한의 **관리 전용 prefix 복구**; C40~C47과 관리 도움말/해당 확인·취소만 |
| 그 밖의 미등록 채널·일반 사용자의 관리 복구 입력 | 무응답·Jev0회; 기존 슬래시 관리 복구는 유지 |
| 운영자 prefix 기능off·Message Content 미준비·봇 채널 접근 불가·DM/봇/webhook | 새 prefix 경로를 열지 않음; 접근 가능한 슬래시 복구 경로 안내는 기존 UI에서 제공 |

정적 allowlist의 기존 채널을 관리 복구 경계로 사용하며 이 버전 계획으로 실제 채널을 추가하지 않는다. 정적 채널이 없거나 접근할 수 없으면 슬래시 복구가 필요하다. 모든 서버 채널을 감시해 관리 의도를 찾는 방식은 사용하지 않는다. 관리 복구 경로의 명령 후보에는 음악·편집을 넣지 않고, 대상 채널 권한과 최신 `AdminGrant`를 서버에서 확인한다.

허용된 복구 채널의 실제 관리자가 보낸 자유 문장은 관리 명령 또는 `no_match`를 고르는 제한된 Jev 판단을 사용할 수 있다. 음악/일반 대화로 판정되면 무응답·무효과로 끝내며 그 판단 호출은 사용량에 포함한다.0dispatch 거절은 미허용 출처·역할·구조상 부적합 입력에 적용한다. 관리 의도가 확정되기 전에는 기존 `MessageResponse.defer()`의 공개 진행 답장도 보내지 않는다. 이 경로를 음악 요청을 실행할 수 있는 범용 채널 허용으로 바꾸지 않는다.

기존 “끄기 후 접두어 무응답” 인수에 대한 변경은 이 제한된 관리자 경로에만 적용한다. 일반 멤버/음악 요청의 무응답과 현재곡 유지·시작 전 승인 무효화는 유지한다. 관리 출처는 서버가 생성하고 원장에 기록하며 입력 문자열/모델이 자칭하지 못하게 한다. 일반 음악 `check_watch`를 건너뛰는 범용 옵션으로 구현하지 않는다. 자신의 끄기/제거 확인은 관리자 트랜잭션으로 한 번 커밋하고, 그 결과로 다른 미완료 음악 요청/승인을 취소한다.

## 공개 메시지와 비공개 결과

현재 `MessageFollowup.send()`는 `ephemeral=True`를 제거한다. 따라서 prefix에서 기존 관리자 handler를 그대로 호출하지 않는다. 등록부의 결과 공개 범위를 응답 생성부터 강제한다.

- 일반 음악 결과에는 현재 권한으로 볼 수 있는 내용만 공개하고 mention escaping을 적용한다. 첨부 내보내기는 기존 참조 형식을 유지한다.
- 관리자 명령·민감한 미리보기는 공개 채널에 **내용 없는 “관리 결과 보기” 버튼**만 남긴다. 클릭한 요청자·서버·채널·최신 관리자 권한을 확인한 interaction에서 ephemeral 결과/확인/페이지를 연다. 공개 placeholder·오류·로그에 채널 목록, 감사 대상, usage 수치를 넣지 않는다.
- 비공개 화면을 텍스트 답장으로 조작하려고 하면 상세를 공개하지 않고 기존 비공개 화면의 버튼을 사용하게 한다. 자연어로 명령을 시작하는 목표와 비공개 표시를 함께 만족시키며 DM fallback은 추가하지 않는다.
- JSON 가져오기는 원래 메시지의 Discord 첨부 한 개 또는 같은 요청자가 명시적으로 답장한 첨부를 읽는다. 파일 수/크기/schema/접근과 읽기 후 권한을 검사한다. 사용자 텍스트가 지정한 임의 파일 경로나 원격 파일 URL을 읽지 않는다.

Discord의 ephemeral 응답은 interaction callback/followup의 메시지 flag이고, 컴포넌트 클릭은 interaction을 만든다. 위 비공개 열기 방식은 이 계약에 따른 설계다. [공식 interaction 응답](https://docs.discord.com/developers/interactions/receiving-and-responding), [컴포넌트](https://docs.discord.com/developers/components/reference). 본문/첨부 접근은 Message Content Intent의 실제 준비 상태도 필요하다. [공식 Gateway 문서](https://docs.discord.com/developers/events/gateway#message-content-intent). 계획 시 확인한 외부 계약이며 실제 계정/클라이언트 검증은05단계에서 수행한다.

## 수명·실패·회귀

원문 삭제·주시 제거/끄기·관리자/DJ 회수·채널 삭제·자료 변경·재시작은 해당 pending과 확인/선택을 무효화한다. 편집한 원문은 기존 요청을 조용히 바꾸지 않고 새 메시지 요청을 요구한다. 재시작 후 자동 음성 입장/재생·질문 재실행·불명 요청 재dispatch는 없다. 영속 idempotency/tombstone·호출 누계와 기존 감사/DB는 보존한다.

관계없는 사용자가 버튼/번호/답장을 복제하거나 다른 채널에서 세션을 참조한 경우0효과·0추가 dispatch를 확인한다. 자연어 관리자 호출 추가와 개인정보 경계 변경은 [0009](../../../docs/decisions/0009-all-command-natural-language-plan.md)로 추적하며 기존 슬래시 관리 Jev0회는 유지한다.
