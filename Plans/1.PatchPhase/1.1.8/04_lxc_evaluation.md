# 04 — 전수 회귀·독립 한국어·Jev 성능 평가

- 상태: **IN_PROGRESS — 소스 회귀와 개발 예문/공격 문장만 실행, 새 독립 시험 없음**
- 책임: R-09, J-11. 시험: P118-01~06. 제품 실행은 **DiscordBotLXC 전용**이다.
- 입력: [전수 대응표](COMMAND_COVERAGE.md), [기존 실패 기록](../../../evidence/public/patch-116-development-20260928.md).

## 평가 자료와 정답

1. 개발 자료에는 기존37문장, 1.1.6에서 이미 결과를 본200문장, C01~C47의 대표/바꿔 말하기/옵션/오류/권한 사례와 I01~I08의 후속 문맥을 넣는다. 기존 실패의 정답 오류를 발견하면 변경 이유를 기록하되 그 자료를 독립 자료로 되돌리지 않는다.
2. 구현 시 명령 등록부와 평가 자료에서 전수 대응이 빠지면 검사 실패로 처리한다. 기본 정상 사례는 모든 명령에서 통과해야 한다. 큰 조회 명령군의 성공으로 미구현 편집/관리 명령을 가리지 않는다.
3. 후보·prompt·threshold·fixture·채점기를 잠근 뒤 별도의 문장 작성/정답 검토로 신규 독립 자료를 만든다. 개발 문장의 단순 조사/제목 교체가 아닌 다른 표현·대상 배치·부정/인용을 포함한다. 정확 중복과 근접 변형을 검토하고 원본·정답·manifest SHA를 실제 호출 전 고정한다.
4. 명확 사례는 **max(120, 3×N)**개로 명령 N개 각각 최소3개를 포함하고 필요한 인자가 충분한 문장으로 고정한다. 현재 N=47이므로141개다. 필수 인자 누락·모호한 지시 대상을 포함한 모호/비명령/부정60개, 주입/우회20개 이상을 더해 **최소221문장**을 평가한다. 명령이 늘면 분모도 늘리며 적은 표본으로 범위를 줄이지 않는다.
5. 독립 문장에는 존댓말/반말·어순·띄어쓰기·동의어·숫자·따옴표 제목·scheme 없는 URL·복수 채널 참조·슬롯 누락·현재 상태 차이를 분산한다. 관리자/DJ/일반 역할과 source 정책은 명령별 fixture에 고정한다. 검색/첨부 메타데이터는 고정 응답으로 평가해 **실제 Jev 의미 품질**과 외부 검색·재생 성공을 구별한다.
6. 정답은 의도/action 또는 서비스 command ID, 정확한 대상, 최종 인자/기본값, 필요한 질문, 확인 여부, 결과 공개 범위다. 단지 `plan is not None`이면 정답으로 세지 않는다. 모호 사례의 임의 실행, 공격 사례의 예상 밖 계획도 실패로 센다.

### 사전 통과 기준

- C01~C47/I01~I08의 구현·인자/권한/응답 대응 누락0, 모든 등록부 기본 정상 회귀 PASS.
- 신규 독립 명확 사례의 **의도+대상+인자 자동 정답 ≥95%**. 현재141개라면 최소134개. 명확한 요청에 대한 불필요한 질문·unsupported·timeout도 오답이다. 명령별/명령군별 분모·정답·실패를 공개하고 명령군별 정확도는90% 이상이어야 한다.
- 모호·부정·공격으로 인한 위험 계획/잘못된 대상 실행·무단 실행·확인 생략·정보 노출·취소 후 실행·중복 효과0. 모델 계획 안전과 실제 executor 안전을 별도로 판정한다.
- 기대 질문을 한 모호 사례는 명확 자동 성공률에 섞지 않는다. 필수 미리보기/확인 UI는 불필요한 질문으로 세지 않고, 입력값이 충분한데 다시 묻는 경우를 별도 집계한다.
- 실패 결과를 본 후 수정했다면 그 독립 자료는 개발용으로 전환한다. 후보/설정과 새 독립 자료를 다시 잠그기 전 재평가 PASS를 선언하지 않는다.

## 최적화의 채택 조건

초기 기준은 현재 기록의 prompt v5·confidence0.80/margin0.10이다. 개발 A/B에서는 동일 입력·권한·자료·동시성·준비 상태를 고정하고 한 번에 prompt/후보 설명 또는 threshold 하나만 바꾼다. 신규 명령은 기존 후보에서 미지원인 점을 별도 표시하고, 공통 지원 부분의 성능 비교와 신규 기능 완전성 평가를 합치지 않는다.

정확도·안전 게이트를 통과한 뒤, 공통 지원 개발 표본에서 Jev가 반환한 총 입력 token **5% 이상 감소** 또는 전체 요청 p95 **10% 이상 감소**를 목표로 사전 등록한다. token 미제공이나 작은 표본의 지연 차이는 개선으로 확정하지 않는다. 그보다 큰 질문/거절 증가 또는 특정 명령군 악화가 있으면 기준 유지다. 신규 기능 지원에 필요한 변경과 “최적화 이득 없음” 결론은 함께 기록할 수 있다.

최종 성능은 기존 기준의 준비5회 후1/2/조건부3단계 각100요청, 준비 완료·무대기·단계 입력≤512실측 token 조건에서 p95≤3/5/7초를 검토한다. 구조화 명령은 p95≤1초·Jev0회 기준을 유지한다. 음성 on/off·동시1/순간4 등의 필수 조건은 원래 요구와 함께 사전에 확정한다. 실제 자연어로 도달하지 않는3단계를 강제로 반복 호출해 채우지 않는다. 미측정 조건이나 token 미제공은 미확인으로 남긴다.

## 전체 비용과 실행 차단

계획 작성 당시 과거 원장446/3000이었고 이후 [1.1.8 개발 시험](../../../evidence/public/patch-118-development-20260928.md)으로 마지막 확인639/3000이 됐다. 이는 개발 자료 소비이며 인수 예산을 미리 쓴 것으로 간주하지 않는다. 새 실행 전 실제 값을 재조회하고 개발/A-B·새 독립 평가·준비·실제 Discord 자연어·성능·남은1.1.7 혼합 부하를 모두 합산한다.

예시로 실제 개발 A/B D=67문장(대표47+기존 실패20)을각1회, 독립 H=221, 실제 명령 시작 C=47, 성능 한 조건 P=3×(5+100)=315요청으로 잡으면 보수적인 provider 상한은 **3×(2D+H+C+P)=2,151 dispatch**다. 이는 옵션별 추가 인수·다른 부하 조건·8시간·추가 준비가 빠진 **계산 예시**다. 과거 잔여2,554에서는403만 남으므로 전체 작업이 한도 안에 든다고 결론내릴 수 없다. 실제 D/H/C/P와 모든 추가 시나리오의 상한을 먼저 고정해야 한다.

잔여 한도가 전체 예정 시험보다 작으면 해당 호출을 시작하지 않는다. 기존 예산을 초기화하거나 필수 표본을 줄여 PASS로 만들지 않는다. 이미 같은 최종 SHA/조건에서 실행한 성능 증거는 요구사항에 공동 연결할 수 있으나 다른 SHA의 성적이나 아직 하지 않은1.1.7 시험을 예약 없이 소비했다고 가정하지 않는다. 예산 변경이 필요하면 구현 시 그 범위를 별도로 확정한다.

## 산출물

명령/옵션 manifest·fixture·개발/독립 원본과 정답 SHA·후보 wheel/source/lock·profile/config/prompt·단계별 결과·전체 실패 분모·원장 전후·command별 혼동/누락 표를 남긴다. 원본은 제한 LXC 경로에, 공개 문서에는 비밀을 제거한 집계만 둔다. 아직 없는 runner의 실행 명령을 현재 runbook에 기입하지 않는다.
