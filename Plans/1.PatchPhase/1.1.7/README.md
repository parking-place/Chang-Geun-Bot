## 현재와 달라지는 점

현재 1.1.7 착수 시 `patch116a`의 첫 PCM은 93/100으로 목표 미달이었다. 같은 오류 코드에 가려진 첫 PCM 전 실패를 고정 코드로 구분하는 `patch117a` 진단 후보를 적용했다. 이 후보도 첫 PCM94/100으로 목표95%에 실패했고, 여섯 실패가 서명 미디어 URL의 HTTPS 응답 실패로 분류됐다. 최종 `patch117b`는 이 오류의 사용자 안내만 보완해 새 SHA의 100회 PCM은 반복하지 않았다. 이 첫 PCM 시험은 Discord에서 실제 소리가 들린 100회 인수가 아니다. 사용자 부분 청취, 합성 회귀, 과거 후보의 백업 복원도 이 버전 전체 PASS를 대신하지 않는다.

현재 봇과 Jev 중계는 DiscordBotLXC의 서로 다른 계정으로 실행한다. 개발 인증서는 30일 유효하고 unit의 자동 부팅 시작은 미활성이다. 이 버전은 현재 배치의 수명·복원·운영 전환 절차를 구현하고 검증한다.

1.1.6의 첫 잠금 200문장 평가는 명확 103/120과 예상 밖 계획 3건으로 **FAIL**이었다. 해당 결과를 통합 품질 PASS로 취급하지 않는다. 사용자는 1.1.7의 백업 검증을 건너뛰도록 지시했다. 외부 암호화 사본·복원 시험은 **SKIPPED — 사용자 지정**으로 기록하며 백업/복구 성공이나 R-06 완료를 주장하지 않는다.

## 선행 조건과 후보 잠금

1. [1.1.4](../1.1.4/README.md)의 미디어 실패 분류와 [1.1.5](../1.1.5/README.md)의 핵심 주시·권한·출처·취소·채널/재시작 회귀가 선행되어야 실제 통합 실패를 원인별로 판정할 수 있다. R-03 전체 완료를 착수 조건으로 요구하지 않으며 W-20의 장시간/상속 잔여를 이 버전에서 함께 닫는다.
2. [1.1.6](../1.1.6/README.md)의 고정 판단 설정·독립 한국어 결과와 [1.1.0](../1.1.0/README.md)~1.1.5의 영향 회귀 증거를 동일 누적 후보에 연결한다. 다른 SHA 결과는 배경 기록으로 구분한다.
3. 백업/runner/계측 설계는 선행 개발과 병행할 수 있다. 최종 음성·부하·복원 인수는 source·wheel·lock·DB/원장 schema·profile/config/prompt·미디어 의존성을 잠근 뒤 수행한다.
4. 시험 뒤 수정이 생기면 변경 영향과 재시험 범위를 기록한다. 판단 경로가 바뀌면 독립 품질 근거도 재검토한다. 과거 버전의 PASS를 새 SHA로 소급하지 않는다.

R-06/R-07의 전체 책임이 이 버전에 있다는 이유로 앞선 변경의 백업·복귀 묶음이나 인증서 만료 점검을 미루지 않는다. 최초 착수와 매 배포 전에 공통 선행 검사를 수행한다.

## 실제 재생과 성능 계약

Jev API Only·API 1.2, 최대 3단계/3 dispatch, 전체 12초·단계 4초/잔여시간 중 작은 값, 조건부 3단계 진입 잔여 1초를 유지한다. 구조화 음악 제어와 주시 설정의 Jev 0회, API 장애 중 기존 음성 재생 유지도 확인한다.

아래 수치와 미실행 판정은 [기존 출시 기준](../../0.DevPhase/RELEASE_CRITERIA.md)과 [1.0.1 실제 인수](../../0.DevPhase/1.0.1/05_live_acceptance_and_release.md)를 승계한다. 목표를 새 측정 결과로 표시하지 않는다.

- 지원 영상 최소 20개를 고정해 준비 5회 후 시작/전환 최소 100회를 수행한다. 같은 시도에서 첫 PCM/Discord 음성 시작/청취를 각각 기록하고 실패 영상 제외·숨은 재시도로 성공 분모를 바꾸지 않는다.
- 시작 성공률 ≥95%, 준비된 음성 연결에서 첫 오디오 p95 ≤10초 목표를 따른다. 시도 전체의 성공/실패/timeout과 소요 시간을 보고하며 총 준비 25초·누적 resolve 15초/startup 10초의 종료 상한을 늘리지 않는다.
- 승인 음원과 후속 버전에서 허용한 YouTube 소스의 혼합 재생을 최소 8시간 연속 유지한다. 곡 전환·일시정지/계속·명시 정지/퇴장·자연어·주시 변경 부하를 별도 시나리오로 배치하고 실제 청취 확인 지점을 사전 고정한다.
- 연속 재생 구간을 깨는 정지/프로세스 종료/네트워크 장애 시험은 정상 8시간 구간과 분리한다. 끊긴 구간을 합쳐 연속 8시간 PASS로 계산하지 않는다.
- 자연어 성능은 1/2/조건부 3단계 각 경로에서 준비 5회 뒤 최소 100요청을 측정한다. 동시 1개/순간 4개, 재생/미재생 조건과 표본 수를 사전에 고정하고 비교 조건을 생략했다면 미실행으로 남긴다. 구조화 제어도 별도 표본으로 p95 ≤1초·Jev0회라는 기존 기준을 확인한다.
- 준비 완료·무대기·단계별 실측 입력 ≤512토큰 조건의 p95 ≤3/5/7초 목표를 유지한다. token 미제공이면 해당 조건 충족은 미확인이다. 성공 지연과 함께 전체 실패·timeout·취소·429 분모를 보고한다.
- 실제 RSS·CPU·이벤트 루프 지연·연결/파일/자식 프로세스 수·원장 누계를 수집한다. 유휴 복귀 후 지속 증가와 음성 끊김을 점검하며 외부 API 내부 시간을 추정 실측으로 기록하지 않는다.

### 비용과 시험 도구

1.1.6의 비교/품질 호출과 이 버전의 준비·성능·8시간 자연어 부하·복구 probe 상한을 합산한다. 계획한 경로대로 진행할 때 성능 한 조건은 `(준비5 + 측정100) × (1 + 2 + 3) = 630 dispatch`다. 경로 분기가 아직 고정되지 않았다면315요청 모두의 최대3단계를 적용한945dispatch를 사전 상한으로 잡는다. 준비 요청을 단일 dispatch로 간주하지 않으며 복수 조건·재측정의 상한도 더한다. 혼합 부하의 요청 빈도·최대 단계는 실행 전에 확정하고 실제 원장 누계와 대조한다.

현재 고정 epoch의 최대 3000 dispatch에서 이미 예약된 호출을 차감한 잔여가 전체 계획보다 작으면 시작하지 않고 부족분을 기록한다. 예산을 맞추려고 필수 표본을 줄여 PASS로 처리하거나 새 run·원장 삭제·재시작으로 초기화하지 않는다. 자동 재시도와 불명 예약 환불도 금지한다.

현재 개발 `korean-eval`은 37문장용이며 checksum을 잠근 첫 200문장 runner는 1.1.6에서 실행됐으나 목표에 실패했다. 경로별 benchmark/8시간 soak runner는 아직 없다. 기존 미디어 probe도 실제 청취와 8시간을 자동 입증하지 않는다. 도구 구현·격리 검증 뒤 실제 실행법을 runbook에 기록한다. 모든 제품 시험은 DiscordBotLXC에서 수행한다.

## 백업·인증서·운영 수명

- 봇 DB, 현재 고정 중계 epoch의 ledger/tombstone, schema·후보·설정 manifest를 일관된 시점으로 묶는다. 계정별 최소 권한으로 백업하고 키는 별도 암호화·접근통제 대상으로 관리하며 공개 manifest에 넣지 않는다.
- [기존 복구 목표](../../0.DevPhase/0.8.0/03_backup_restore.md)의 일일 7개·주간 4개, RPO 24시간·RTO 60분을 승계한다. 구현 전에 서버 외부 보관 대상·담당·용량·보존/실패 알림 경로를 정하고 실제 외부 사본으로 측정한다.
- DiscordBotLXC의 빈 격리 경로에 복원해 자동 Discord 접속/음성 재생을 차단한다. 주시/꺼짐·대기열·만료 승인·확인 토큰 무효화·중복 효과 0을 대조한다.
- 복원으로 예약 누계가 줄거나 불명 요청이 다시 dispatch되지 않아야 한다. 백업 이후 최신 원장/tombstone과 안전하게 대조할 수 없으면 hosted 호출을 차단한 채 복원 검증만 진행한다.
- rollback은 이전 바이너리와 호환되는 이전 봇 DB 묶음으로 수행하고 최신 DB 원본을 보존한다. 호출 예산·tombstone은 현재까지의 보존 누계를 유지하며 오래된 백업으로 되감지 않는다.
- 만료 14일/7일/1일 전 확인·알림을 계획값으로 설정하고 만료/호스트 불일치 인증서를 거절한다. 갱신 후 양쪽 TLS trust·연결 풀 무효화·무료 readiness·키 읽기 권한을 검증한다.
- 현재 구현한 `scripts/check_gateway_lifetime.py`는 DiscordBotLXC root의 읽기 전용 사전 점검이다. 만료 임계값에서는 비정상 종료해 운영자가 알림/갱신 절차를 시작할 수 있지만, 정기 실행·알림 수신자·인증서 자동 갱신 자체는 아직 구현/인수하지 않았다.
- 서비스 시작 순서·drain·종료·재시작·재부팅 후 준비 상태를 검증한다. 자동 부팅 시작/운영 경보는 운영 전환 범위와 수신 대상을 확정한 뒤 적용하고 재시작 시 자동 음성 입장·재생은 금지한다.
- OpenJevLXC에 새 작업을 수행하지 않는다. 역사 백업을 현재 최신 원장으로 간주하지 않으며 기존 원본·DB·후보·예산을 삭제하거나 덮어쓰지 않는다.

## 완료·중단·복귀 조건

개발 인수에는 다섯 단계 증거, P117 전건 결과와 누적 기능/안전/독립 품질 게이트의 대조가 필요하다. 정식 VERSION·태그·출시는 기존 미완료 게이트와 같은 대상의 필수 인수를 충족한 뒤 별도 출시 절차로 판단한다.

예산 부족·청취/재생 목표 미달·위험 실행·자원 고갈·원장 누계 감소·백업 무결성 실패·만료 인증서는 시험/후보 적용을 중단하는 조건이다. 실패 시 현재 증거와 원본을 보존하고 이전 호환 바이너리/봇 DB로 복귀하며 최신 호출 누계·tombstone을 유지한다. 복구 안전성이 불명확하면 자연어 접수를 닫고 구조화 기능의 검증된 범위만 유지한다.
