# 1.1.1 — Jev 연결·준비 상태·응답 경계

- 상태: **PLANNED — 문서만 작성, 구현·시험·배포 미실행**
- 범위: **J-02, J-03, J-08**
- 목적: 연결 재사용과 준비 상태 확인의 실제 이득을 측정하고, 큰/느린 응답·혼잡에서도 판단 기한과 호출 예산을 지킨다.
- 공통 기준: [실행 규칙](../EXECUTION_RULES.md), [항목 배정](../ITEM_COVERAGE.md), [상태](../STATUS.md), [시험표](../TEST_MATRIX.md).

## 현재와 바뀔 점

현재 bot→중계와 중계→Jev 경로는 호출마다 `AsyncClient`를 만들며, 자연어 입력마다 무료 health를 직렬 확인한다. 두 판단 HTTP 경로는 응답 전체를 받은 뒤64KiB 상한을 검사한다. 동일 요청 재사용·합류와 활성1/대기4는 이미 있다.

이 버전은 client 수명·제한된 풀·health 합류/짧은 캐시를 비교하고 수신 도중 응답 상한을 적용한다. 연결 비용이 실제 병목인지 먼저 측정하며, 개선 폭을 확정하거나 유료 호출 감소로 바꾸어 설명하지 않는다.

| ID | 이 버전의 책임 | 제외·후속 경계 |
| --- | --- | --- |
| J-02 | 봇/중계의 client 생성·재사용·종료와 유한 풀 | worker/활성 dispatch 증가, 인증/TLS 약화 금지 |
| J-03 | profile/config에 결합한 readiness 합류·짧은 캐시 비교 | 사용자 권한·주시 상태·실행 승인 캐시 제외 |
| J-08 | 오류 분류·수신 상한·혼잡 안내·지속 장애 접수 차단 비교·기한 회귀 | 자동 재시도·숨은 paid probe·새 제공자 fallback 제외 |

## 선행 의존성

1. [1.1.0](../1.1.0/README.md)의 권한 분기 회귀·J-01 지표·R-08 오류 대응표가 개발 기준으로 준비되어야 한다.
2. 변경 전 동일 후보의 warm/cold·동시1/순간4·음성 부하 유무 기준을 고정한다. 과거 transport3회 수치를 전체 NL 기준으로 대체하지 않는다.
3. 봇 종료와 중계 lifespan/drain, 현재 TLS/profile/token 갱신 경계, 유휴 연결 실패 처리를 설계한다.
4. 유료 비교 표본·준비 호출·최대3단계의 총상한을 먼저 계산하고 현재 고정 epoch의 남은 예산과 대조한다.
5. 품질용 개발 회귀를 별도 유지한다.1.1.6의 미래 held-out 점수는 이 후보의 과거 검증을 대신하지 않는다.

## 사용자·API 계약

- Jev API Only·API1.2·최대3dispatch·전체12초/단계4초·활성1/대기4·retry0·redirect0를 그대로 유지한다.
- 내부 loopback TLS 검증과 hosted 키의 중계 전용 접근, `trust_env=False`를 유지한다. 연결 재사용은 인증값 공유 범위 확대가 아니다.
- 요청별 남은 시간을 호출에 전달한다. 공유 client의 전역 timeout을 요청마다 덮어쓰지 않는다. pool 대기도 요청 기한에 포함한다.
- health는 중계 준비 상태 확인이며 Jev 성공/계정 예산의 보장이 아니다. 시작 시 확인과 매 응답의 provider/profile/config binding 검증은 유지한다.
- health TTL·풀 크기는 설계 단계에서 후보값/비교 조건을 고정한다. 아직 채택된 실행 설정은 없으며 오류/재시작/설정 변경 때 무효화한다.
- 응답이64KiB를 넘으면 더 읽지 않고 안전하게 종료한다. 청크 수신/파싱/정리의 경과 시간도 기존 기한에 포함한다.
- 전송 취소·연결 유실·외부429·큰/깨진 응답도 예약 호출을 환불하거나 새 ID로 재전송하지 않는다. 늦은 결과는 실행하지 않는다.
- 사용자에게 혼잡/일시 장애와 슬래시 대안을 안내하며 내부 endpoint·토큰·원문 provider 응답을 노출하지 않는다.

## 측정과 채택 판단

연결 재사용, health 합류, TTL 캐시는 각각 비교하고 여러 변경의 효과를 한 수치로 합치지 않는다. health 왕복 감소는 무료 내부 경로의 감소로 기록한다. 성공 지연 p50/p95와 실패/timeout 수·시간, 실제 신규 dispatch, RSS/연결 수를 함께 보고한다.

기준보다 나아지지 않거나 표본 편차를 벗어나지 못하면 해당 최적화는 **기준 유지**로 판정하고 변경을 채택하지 않는다. 이것은 성능 개선 PASS가 아니다. 응답 크기/기한/오류 경계의 안전성 변경은 그 자체의 시험으로 평가하며 성능 가정을 성공 근거로 삼지 않는다.

지속 장애에서 신규 자연어 접수를 잠시 막는 후보도 설계·mock 비교에 포함한다. 오류별 진입 조건·최대 차단시간·복구 조건을 고정하고, 기준안과 정상 요청 오차단/추가 실패 호출을 비교해 채택 또는 기준 유지를 결정한다. 무료 health만으로 hosted 복구를 확정하지 않으며 새 명시 사용자 요청 외 숨은 유료 탐침·자동 재시도는 추가하지 않는다. HTTP timeout 설정만으로 경과 시간 경계를 충족했다고 판단하지 않는다.

## 완료·중단·복귀 조건

- 개발 완료: J-02/J-03의 채택 또는 근거 있는 기준 유지 판정, J-08 안전 경계, P111 전건의 필요한 증거와 고정 후보/복귀 자료를 남긴다.
- 정식 출시: 해당 exact candidate의 필수 회귀·품질/성능·운영 게이트가 필요하다.1.1.0 기반 통과나 후속 최종 평가를 그대로 승계하지 않는다.
- 중단: 호출/worker 상한 증가, TLS 검증 우회, 예약 환불/재시도, 기한 후 실행, 연결/메모리 누수, 실패 은폐를 발견하면 인수를 중단한다.
- 복귀: 새 접수를 중단하고 정상 drain·기한 결과를 기록한 뒤 이전 bot/gateway wheel·설정으로 전환한다. 소유권·원장·고정 epoch와 예산은 그대로 보존한다.
- 설정 호환이 깨지면 이전 설정/바이너리 묶음으로 복귀한다. 운영 DB·이전 후보는 삭제하지 않고 자동 음성 재연결/재생을 하지 않는다.
