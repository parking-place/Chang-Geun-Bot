## R-01 — 새 주시 채널의 다후보 경로

[Pipeline.interpret](../../bot/src/changgeun/nlp/pipeline.py)의 과거 코드에서는 각 dispatch와 단일 후보 완료에 `request_policy()`를 사용했지만 2단계 직전 `authorize(...)`에는 `self.policy`를 전달했다. [authorize](../../bot/src/changgeun/domain/models.py)는 텍스트 채널 허용 범위를 검사한다. 1.1.0 개발 후보에서 해당 지점을 입증된 요청 정책으로 통일했다.

일반 슬래시/멘션 허용 목록에는 없고 `/주시 추가`로 등록한 채널에서 1단계 후 여러 후보가 남는 요청을 격리 mock으로 재현했다. **2단계 전 정적 정책 오거절을 확인하고 수정한 개발 결과이며, 실제 Discord·3단계 전건 인수는 아직 아니다.** 전체 권한 검사를 느슨하게 하는 수정으로 해결하지 않는다. [부분 실행 기록](../../evidence/public/patch-110-development-20260928.md)을 따른다.

재현·통과 조건:

1. 정적 허용 채널과 신규 동적 주시 채널을 분리하고 서버가 입증한 prefix 원장·동일 DJ/음성·동일 목록 상태를 준비한다.
2. 유효한1단계 단일 후보,2단계 다후보, 근거 있는3단계 참조 요청을 각각 비교한다. 실제 Jev 이전에 mock으로 분기/호출 수를 고정한다.
3. 정상 동적 요청은 필요한 다음 단계에 도달해야 한다. 가짜 origin/request ID, 일반 슬래시/멘션의 허용 범위 확대는 모두 거절한다.
4. 판단 중 채널 제거·서버 끄기·DJ 해임·대상 변경은 여전히 미실행이어야 한다. 취소 뒤 추가 dispatch/커밋/음성 시작0을 확인한다.
5. 수정이 필요하면 공통 출처 정책의 적용 위치와 해당 회귀를 함께 기록한다. 이전328건 PASS만으로 새 분기를 검증했다고 하지 않는다.

## R-02 — 재생 실패를 먼저 설명할 수 있게

기존20영상×5 시험에서7건이 실패했다. 같은 영상의 다른 회차는 성공했고 상세 원인은 아직 분류되지 않았다. 고정 영상 제외, 숨은 재시도, 제한시간 확대를 성공률 개선으로 계산하지 않는다. [당시 실패 기록](../../evidence/public/youtube-prefix-20260928.md)을 유지한다.

메타데이터/지원 조건, resolver, 네트워크, FFmpeg 시작, 첫 PCM, Discord 음성 시작을 구분한다. 허용되지 않는 길이·비공개/삭제·라이브 등 지원 조건과 일시적 준비 실패를 구별하고 원문 upstream 응답·signed URL은 남기지 않는다. 판별할 수 없는 원인은 `unknown`으로 보존한다.

공통100회 표본에서 시도 전체의 성공률·실패 수를 보고하고 성공 지연 p50/p95와 실패/timeout 시간을 별도로 낸다. 첫 PCM 성공은 Discord에서 소리가 들렸다는 뜻이 아니다. 실제 음성 인수는 R-05에서 이어간다.

## R-03 — 주시 관리의 실제 수명

[W-01~20](../0.DevPhase/TEST_MATRIX.md)과 [1.0.3 Phase5](../0.DevPhase/1.0.3/05_acceptance_and_rollout.md)의 미완료 조건을 이어받는다. 새 기능 요구로 다시 등록하지 않는다.

- 주시2/미주시1 채널에서 추가·제거, 서버 관리자/DJ 단독/일반 사용자 권한, 타인의 확인 버튼을 확인한다.
- 현재곡 유지, 준비 중 곡의 승인 만료, 다른 출처 곡 보존, 재등록으로 옛 승인 부활 없음 등을 실제 음성과 대조한다.
- 채널 삭제·권한 상실/복구·Gateway 재연결·빈 목록/꺼짐 후 재시작을 확인한다.
- 목록11~20개 페이지, 점검403/429/시간 초과, 감사 보존 삭제를 점검한다. 실제 채널을 무작정 늘리는 대신 필요한 범위를 격리한다.

## R-04·R-05 — 품질과 성능의 정식 증거

독립200문장은 개발37문장과 분리한다. 명확한 지원 요청120개·모호/비명령/부정60개·우회/교란20개를 기준으로 정답 action/대상/확인 필요를 고정한다. 명확한 요청95% 목표와 위험 실행0을 유지한다. 새 표현 지원을 조정한 개발 데이터로 최종 점수를 내지 않는다.

기존 [성능·8시간 계획](../0.DevPhase/0.9.0/04_performance_soak.md)의1/2/3단계별 표본과 음성 혼합 부하를 따른다. 성공 사례만 집계하거나 통신 실패를 지연 표에서 숨기지 않는다. 같은 LXC의 봇900MiB/중계384MiB 상한에서 큐 대기·프로세스·RSS·재시작을 함께 본다. 실제 서비스 자원 상태는 시행 시 다시 측정한다.

현재 `korean-eval`은 개발 세트용이다. 독립 평가/benchmark/soak 도구를 이미 완성된 실행 명령으로 문서에 적지 않는다. 측정 runner를 구현·검증한 뒤 실제 실행법을 기록한다.

## R-06·R-07 — 현재 배치의 복구

봇 DB와 새 고정 중계 epoch의 ledger/tombstone을 현재 경계에 맞춰 일관성 백업하고 격리 경로에서 복원한다. 복원 전후 예약 호출 수·중복 식별·주시 설정·승인 만료·자동 음성 재생 금지를 대조한다. 이전 바이너리에는 이전 DB 묶음을 사용한다. 원본과 최신 DB를 삭제/덮어쓰기하지 않는다.

이전 OpenJevLXC의 역사 백업은 최신 전체 원장으로 간주하지 않는다. 같은 서버 안의 사본만으로 서버 전체 손실 복구를 확인했다고 하지 않는다. 현재 배치의 서버 외부 암호화 보관 대상과 보존 주기·복구 목표를 다음 계획에서 결정한다.

개발 인증서 만료 전 확인, 갱신 후 검증, 키 접근권한, 후보 manifest/설정 binding과 배포 증거를 연결한다. 서비스 자동 부팅 시작과 운영 경보는 실제 운영 전환 범위를 확정한 후 적용한다. 이번 문서 작성으로 서비스를 재시작하거나 운영 설정을 바꾸지 않는다.

## R-08 — 원인은 운영자가, 다음 행동은 사용자가 알 수 있게

현재 [natural_input](../../bot/src/changgeun/discord_adapter/client.py)은 여러 예외를 공통 문구로 처리한다. 모호한 요청, 권한 거절, 대상 변경, 주시 해제, Jev 한도/일시 장애, 미디어 준비 실패를 분류하면 사용자와 운영자의 대응이 쉬워진다.

사용자에게는 “목록을 골라줘”, “주시 설정이 바뀌어 취소했어”, “자연어 처리가 잠시 어려워. 슬래시 명령을 사용해줘”처럼 해당 상태에서 가능한 행동을 안내한다. 내부 endpoint·키·실제 서버 ID·API 원문을 노출하지 않는다. 같은 요청을 자동 재실행하지 않고 새 명시 요청을 받는다. 기능 F-04, 계측 J-01과 함께 검토한다.
