# Jev API 최적화 검토

상태: **J-01~09 개발 후보·비교를 수행했으나 전체 인수 미완료**. J-07 축약 prompt는 개발 자료에서 입력 token을 줄였지만 독립 품질 FAIL로 운영 미적용, J-09 임계값은 기준 유지다. 현재 결과는 [계열 현황](STATUS.md)과 [1.1.6 기록](../../evidence/public/patch-116-development-20260928.md)을 따른다. 아래는 편성 당시 제안·차이 분석이다. 실제 제공자는 Jev API Only다. 로컬 모델 최적화나 제공자 교체가 아니라 봇·중계의 요청 경로를 개선한다. 현재 계정의 가격/전체 사용량이나 새로운 Jev API 기능을 가정하지 않는다.

## 이미 구현한 최적화

- 실행 후보가 하나로 완성되면1단계 뒤 종료하고, 근거가 있는 참조만 조건부3단계를 사용한다.
- 동일 요청/단계는 결과 재사용과 진행 중 합류를 지원한다. 이를 “캐시 신규 도입”으로 다시 제안하지 않는다.
- 미허용 채널/호출어 없는 메시지를 사전 차단하며 구조화 명령·관리 명령은 Jev0회다.
- 후보/최소 문맥·익명화를 적용하고 최대3dispatch·전체12초·단계4초·활성1/대기4를 유지한다.
- 실패/불명 호출의 원자적 예약·영속 예산과 요청 tombstone을 보존한다. 자동 재시도는 없다.

근거: [Pipeline](../../bot/src/changgeun/nlp/pipeline.py), [DecisionService](../../inference/src/changgeun_inference/service.py), [Ledger](../../inference/src/changgeun_inference/ledger.py), [실행 계약](../0.DevPhase/INFERENCE_PROFILES.md).

## J-01 — 계측을 먼저

현재 [개발 probe](../../scripts/probe_pipeline.py)는 전체 elapsed/단계 수를, [전송 probe](../../scripts/probe_transport.py)는 단계 왕복 시간을 기록한다. 운영 관측 모듈과 세부 구간 집계는 충분히 구현되지 않았다. 과거3회 API 측정이나37문장 점수로 병목과 p95를 일반화하지 않는다.

제안 지표:

- 접수/전처리, 최신 권한/주시 검사, DB snapshot/후보 생성, health, 내부 왕복, 중계 대기, 외부 provider, 최종 검증/응답 시간을 구분한다.
- 요청별 단계 수, 신규 dispatch, 같은 요청의 캐시/합류, 사전 거절, 모호함, 권한/주시 취소, timeout·실패를 별도 집계한다.
- API가 반환한 `input_tokens`만 실측으로 사용한다. 누락은 unknown이며 문자/바이트 수를 token 수로 표시하지 않는다. hosted forward와 미공개 revision은 unavailable을 유지한다.
- source/candidate/profile/config/prompt/data 버전과 시험 조건을 함께 기록한다. 운영 자료에는 원문·제목·실제 Discord ID·키·signed URL을 넣지 않고 집계 중심으로 보존 기간을 정한다.

서로 다른 프로세스의 monotonic 절대값을 직접 빼지 않는다. 각 프로세스의 구간 소요 시간을 사용한다. 외부 API 내부 계산 시간은 관측되지 않으므로 provider 왕복 시간과 구분한다. API1.2 응답에 계측 필드를 추가한다면 엄격 스키마/클라이언트 호환성을 먼저 정하고, 우선은 내부 집계로 시작할 수 있다.

## J-02 — 연결을 매번 열지 않기

현재 [GatewayClient.ready/choose](../../bot/src/changgeun/nlp/client.py)와 [HostedProvider.decide](../../inference/src/changgeun_inference/providers.py)는 각 호출마다 `AsyncClient`를 생성/종료한다. 프로세스 수명 안에서 제한된 풀을 재사용하면 연결 준비 비용을 줄일 가능성이 있다. **현재 지연에서 얼마나 차지하는지는 아직 측정하지 않았다.**

봇 시작/종료와 중계 lifespan/drain에 각각 생성·정리 책임을 둔다. 공유 client의 전역 timeout을 요청마다 수정하지 않고 남은 요청 시간을 호출별로 전달한다. 인증서/키/profile 변경 때 이전 연결을 무효화한다. 취소·실패·유휴 연결 만료와 테스트 transport의 수명도 검증한다.

풀 상한은 측정 후 정하며 활성 model dispatch1을 늘리는 수단으로 사용하지 않는다. health가 길게 실행 중인 판단의 연결 점유 때문에 막히는지도 확인한다. TLS 검증, `trust_env=False`, redirect0·retry0는 유지한다.

HTTPX는 연결 풀 활용을 위해 범위를 정한 client 재사용과 명시적 종료를 안내한다. [공식 Async 문서](https://www.python-httpx.org/async/), [풀 상한 문서](https://www.python-httpx.org/advanced/resource-limits/)를2026-09-28 확인했다. 이 문서는 라이브러리 동작의 근거이며 Jev endpoint의 성능 보장이 아니다.

## J-03 — health 왕복 줄이기

현재 [natural_input](../../bot/src/changgeun/discord_adapter/client.py)은 자연어 해석 전에 `gateway.ready()`를 직렬 호출한다. 시작 시 확인은 유지하면서 동시 요청의 health를 하나로 합류시키거나 짧은 준비 상태 캐시를 비교한다. TTL은 실험값으로 정하며 현재 채택된 설정이 아니다.

캐시할 것은 provider/profile/config에 결합한 **중계 준비 상태뿐**이다. 사용자 권한·주시 상태·대상 버전·재생 승인을 캐시해 생략하지 않는다. 중계 오류/재시작/설정 변경 때 무효화하고 각 `choose` 응답의 binding 검증은 그대로 수행한다. 오래된 ready가 실제 요청 성공을 보장하지 않는다는 전제를 유지한다.

health는 유료 판단이 아니므로 이 개선의 효과를 Jev 호출 비용 절감으로 표시하지 않는다.

## J-04 — 이미 명백한 권한 거절은 먼저

현재 pipeline의 사전 정책 검사는 조회 권한을 기준으로 하고, 구체 행동의 권한 검사는 첫 판단 뒤에도 수행한다. 규칙이 이미 단일 행동을 만들었거나 모든 후보가 동일 권한을 요구할 때, 명백한 DJ/음성 권한 거절을 첫 유료 호출 전에 확인하는 방안을 검토한다.

해당 거절 경로는 dispatch1회를0회로 줄일 여지가 있다. 일반 사용자의 조회/곡 제안과 권한이 섞인 후보를 잘못 차단하면 안 된다. 최신 actor와 입증된 동적 prefix 정책을 사용하고 [R-01의 권한 경로 점검](03_STABILITY_AND_ACCEPTANCE.md)을 선행한다. 첫/후속 판단 뒤와 실행 직전의 재검사는 모두 유지한다.

이는 자연어 동작을 규칙만으로 실행하는 fast path 제안이 아니다. 정상 자연어 의미 판단의 기존 Jev 단계와 확인 정책을 유지한다.

## J-05 — 데이터 조회 범위 줄이기

`Pipeline._snapshot()`은 세션·모든 목록/항목·대기열·곡을 가져온다. 각 판단 전에도 같은 snapshot을 만들지만 즉시 검사하는 값은 세션 version/generation이다.

초기 후보 생성 snapshot과 단계 전 최소 버전/세대 조회를 분리하고, 이후 실제 후보 검색에 필요한 자료만 가져오는 방안을 순서대로 검토한다. 먼저 조회 범위를 줄인 뒤 자료 크기별 병목이 남을 때 색인/검색 구조를 평가한다. 검증 없이 모든 DB 작업을 병렬화하거나 별도 스레드로 옮기지 않는다.

검증은 작은/큰 카탈로그·긴 큐·동시 편집에서 SQL 횟수와 행 수, 시간/메모리를 비교한다. 목록/큐 버전·현재곡·주시 세대·확인 snapshot이 달라지면 기존처럼 충돌 또는 미실행이어야 한다. 실행 직전 최신 검사를 성능 개선을 이유로 삭제하지 않는다.

## J-06 — Jev에 보내기 전 정답 후보를 놓치지 않기

현재 후보 생성에는 이름 부분 일치·전체 곡/별칭 순회와 후보10개 제한이 있다. 정답이 후보에 없으면 Jev가 올바른 답을 선택할 수 없다. 정확한 이름/별칭 우선, 부분 일치의 안정적 순위, 동일 제목 충돌의 선택 화면을 검토한다.

`정답 후보 포함률`과 `포함된 경우의 Jev 선택 정확도`를 따로 기록한다. 카탈로그를 키워 상한 앞뒤의 정답·중복 제목·짧은 제목·따옴표/부정문을 평가한다. 단순히 후보 수를 늘려 정확도·token·지연을 악화시키지 않는다. 오타 유사도만으로 파괴적 행동의 대상을 확정하지 않는다.

## J-07 — 프롬프트와 설명 축약

현재 같은 `INSTRUCTIONS`가 모든 단계에 전달된다. 중복 설명 축약이나 단계별 문구를 한 번에 하나씩 비교한다. 부정문, 저장 목록과 대기열의 구별, 복합 요청 미지원, 비신뢰 데이터 처리, clarify 조건은 유지한다.

기존 confidence0.80/margin0.10을 우선 고정하고 prompt만 비교한다. prompt/내용/설정 hash를 새 고정 후보에 연결하며 실행 중 원장을 지우거나 현재 고정 epoch의 예산을 초기화하지 않는다. 별도 실험 식별자는 결과 구분용이지 새 무료 예산을 만드는 수단이 아니다.

token/비용 절감을 수치로 말하려면 API 반환 usage와 확인된 과금 기준이 필요하다. Jev가 지원한다고 확인되지 않은 prompt cache·batching·temperature/max-token 인자를 추가하는 계획은 이번 추천에 포함하지 않는다.

## J-08 — 오류·응답 경계

현재 중계는 큐 가득 참을429로 반환하고 여러 provider 실패를 `provider_failed`로 묶는다. 봇 자연어 경로도 공통 실패 안내를 사용한다. 내부 혼잡·외부429·timeout·인증·예산 소진을 비밀 없는 코드로 분류해 [R-08/F-04](03_STABILITY_AND_ACCEPTANCE.md)의 안내에 연결한다.

두 Jev HTTP 경로는 현재 응답 전체를 받은 뒤64KiB를 검사한다. 스트리밍 수신 도중 상한을 확인하고 초과/취소 시 연결을 정리하는 변경도 검토한다. 정상 응답·깨진 JSON·초과 응답·느린 청크·취소를 시험하고 원장 예약은 환불하지 않는다. [HTTPX streaming 안내](https://www.python-httpx.org/async/)가 정리 책임의 참고 근거다.

HTTPX의 connect/read/write/pool timeout은 각 네트워크 작업의 한도다. 전체12초·단계4초의 경과 시간 경계를 대체하지 않는다. 연결 재사용/응답 수신을 바꿀 때도 절대 기한과 늦은 결과 거절을 함께 확인한다. [공식 timeout 문서](https://www.python-httpx.org/advanced/timeouts/)를2026-09-28 확인했다.

지속 장애 시 신규 자연어 접수를 잠시 막는 방식은 후속 실험 후보로 둔다. 도입한다면 복구 조건/최대 차단 시간을 정하고 무료 health를 과신하지 않는다. 실패한 요청 자동 재시도·새 ID 재발행·숨은 유료 탐침은 추가하지 않는다.

## J-09 — 임계값은 속도 수단으로 낮추지 않기

현재 [개발 프로필](../../deploy/profiles/eval-jev-api-single-lxc-v1.yaml)은 confidence0.80/margin0.10을 사용한다. 확인율만 줄이려고 낮추지 않고 위험 계획0·정확한 대상·불필요한 명확화·단계 수·지연을 함께 비교한다.

단계별 임계값은 별도 설정/계약 변경 후보로1.1.6의 비교/채택 판정에 포함한다. 개발 세트에서만 조정한 뒤 고정하고 독립200문장으로 평가한다. model probability를 보정된 실제 성공확률로 해석하지 않는다.

## 비교 실험의 기록 규칙

1. J-01로 기준을 측정하고 변경은 하나씩 비교한다. warm/cold·무재생/실제 음성 부하를 분리한다.
2. 접수요청 전체에 대해 신규 dispatch 합계/요청 수,0/1/2/3단계 분포, 오류/거절/취소율을 기록한다. 실패를 늘려 호출 수만 낮춘 결과는 개선이 아니다.
3. 성공 p50/p95와 실패/timeout 수·소요 시간을 함께 낸다. 양쪽 표본 수·기능/안전 정확도·시험 조건을 고정하고 측정 편차보다 작은 변화는 결론을 보류한다.
4. 개발N문장을 기준/후보 양쪽에서 최대3단계로 평가하면 상한은 `2 × N × 3 + 준비 호출`이다. 실제 예약은 원장으로 센다. 시작 전 현재 잔여예산과 누적 실험 상한을 확인하고 부족하면 중단한다.
5. 독립 품질/성능/장시간은 기존 출시 게이트를 따른다. 준비 완료·무대기·입력 조건을 충족한 NL p95의 기존3/5/7초 목표는 보장값이 아니다. token을 확인할 수 없으면 해당 조건을 충족했다고 쓰지 않는다.
